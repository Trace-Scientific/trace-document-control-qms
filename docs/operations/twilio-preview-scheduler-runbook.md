# Twilio preview scheduler activation runbook

Status: PR 24 deployment-readiness slice
Environment: Railway development preview only

This runbook activates the PR 23 Twilio delivery-status monitoring contract in the existing Railway development preview. The preview remains synthetic data only and is not validation or production evidence.

## Boundary

- This procedure applies only to the Railway development preview.
- Do not use `traceqms.com` or any protected validation/production hostname.
- Do not enter PHI, PII, customer records, laboratory records, regulated records, or controlled quality evidence.
- Do not treat successful preview execution as validation evidence.
- Protected AWS validation/production provisioning remains paused and unchanged.
- This scheduler observes Twilio delivery status only; it cannot send, replay, or requeue SMS messages.

## Preconditions

Before configuring the scheduler:

1. PR 23 must be merged to `main`.
2. The `qms-preview` service must be healthy at its assigned HTTPS Railway domain.
3. `CRON_SECRET` must already exist on the application service and contain at least 32 random characters.
4. The preview database must have all committed Prisma migrations applied, including `PlatformScheduledOperationState`.
5. Any Twilio connection used in preview must use synthetic/test-safe configuration only.

## Create the scheduler service

Create a separate Railway cron service. Do not run the cron loop inside the long-running web service.

1. Create a new Railway service from `Trace-Scientific/trace-document-control-qms` on branch `main`.
2. Name it `twilio-delivery-status-monitor`.
3. Set the Start Command to:

   `node scripts/run-twilio-delivery-monitoring.mjs`

4. Set the Cron Schedule to:

   `*/15 * * * *`

   This invokes the reviewed PR 23 contract every 15 minutes UTC.

5. Set Restart Policy to `Never` so each scheduled run exits after one request.
6. Do not attach a public domain to the cron service.
7. Do not configure a health check on the cron service.
8. Configure `APP_BASE_URL` with the HTTPS URL of the existing `qms-preview` application service.
9. Configure `CRON_SECRET` with the same secret used by the application service. Use Railway service variables; never commit or paste the secret into source control.
10. Do not configure Twilio provider credentials on the cron service. Provider credentials remain resolved by the application through the governed credential boundary.

## One-time qualification of the preview scheduler

Before relying on the recurring schedule:

1. Confirm `PLATFORM_SCHEDULER_CONFIGURED` is absent or not equal to `true` on `qms-preview`.
2. Use Railway's one-time execution/redeploy controls to run `twilio-delivery-status-monitor` once.
3. Confirm the runner exits successfully.
4. Confirm the log shows a successful JSON response from `/api/internal/platform/twilio-delivery-monitoring` and does not print `CRON_SECRET` or provider credentials.
5. In the platform health workspace, confirm the scheduler operation has recorded a recent successful heartbeat after the application refreshes its health snapshot.
6. Confirm no outbound SMS was generated by the scheduler execution.
7. Confirm any provider-status error is surfaced as monitoring evidence/alert only and does not create a retry or replay action.

Only after those checks pass, set the following application-service variable on `qms-preview`:

`PLATFORM_SCHEDULER_CONFIGURED=true`

Then redeploy/restart the application service as required for the environment variable to take effect.

## Expected health behavior

After scheduler declaration:

- scheduled-task health should report healthy when the successful heartbeat remains within the PR 23 freshness window;
- scheduled-task health should degrade if no successful run is recorded within 30 minutes;
- scheduled-task health should degrade after consecutive scheduler failures;
- integration health may separately degrade for Twilio downstream delivery failures or provider-status polling errors;
- none of those health states authorize automatic SMS resend.

## Failure handling

If the one-time execution fails:

1. Leave `PLATFORM_SCHEDULER_CONFIGURED` unset or false.
2. Confirm `APP_BASE_URL` is HTTPS and points to the current preview application service.
3. Confirm the cron service and application service use the same `CRON_SECRET` without exposing its value.
4. Confirm `/api/health/readiness` on `qms-preview` returns HTTP 200.
5. Confirm the latest application deployment applied all committed migrations.
6. Review the bounded runner error and application logs.
7. Do not repeatedly trigger the job if the prior run is still active; PR 23 also enforces a database lease for overlap protection.
8. Do not bypass the machine-authenticated endpoint by calling Twilio directly from the cron service.

## Disable or rollback

To disable recurring preview monitoring:

1. Disable or delete the `twilio-delivery-status-monitor` cron service.
2. Remove or set `PLATFORM_SCHEDULER_CONFIGURED=false` on `qms-preview`.
3. Preserve any relevant synthetic defect evidence before deleting preview resources.
4. Do not modify the protected AWS environment as part of this preview rollback.

## Security invariants

- The runner follows redirects with `redirect: "error"` and therefore does not forward the bearer secret to a redirected origin.
- The runner requires HTTPS.
- The runner requires a `CRON_SECRET` of at least 32 characters.
- The cron service contains no provider credential bundle.
- The cron service cannot enqueue an integration delivery or requeue a dead letter.
- The cron service cannot POST a Twilio Message.
- A missed callback or downstream Twilio failure remains an observation/reconciliation concern, never permission to resend automatically.
