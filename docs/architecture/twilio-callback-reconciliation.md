# Twilio Callback-Driven Delivery Reconciliation

Status: PR 21 integration hardening
Baseline: `main` at `c3072a303acfcd443991dbd3beb7ea0fb652a742`

## Purpose

Apply the verified Twilio SMS status events introduced in PR 20 to the PR 19 delivery-reconciliation model without allowing a provider callback to create a new outbound send, grant authority, or trigger an automatic duplicate retry.

## Trust sequence

A Twilio callback can affect a governed delivery only after the existing PR 20 adapter has verified the configured callback origin, Twilio account identity, exact URL/form signature, Message SID, reviewed status value, and signed delivery correlation key.

After verification, the inbound service locks the matching `PlatformIntegrationDelivery` using the active integration `connectionId` plus the persisted outbound `idempotencyKey` carried as the signed `deliveryKey`.

If a provider object ID is already recorded, the callback Message SID must match it exactly. A mismatch rejects the inbound receipt rather than overwriting correlation evidence.

## Status semantics

Twilio message status and Trace outbound-operation status are intentionally separate concepts.

A signed Twilio status callback proves that Twilio created the outbound Message identified by `MessageSid`. Therefore, when the Trace delivery is `RECONCILIATION_REQUIRED`, any verified Twilio status event resolves the ambiguity as `SUCCEEDED` from the platform-to-provider delivery perspective.

The actual downstream message state remains visible in `providerOutcome`, for example:

- `TWILIO_QUEUED`
- `TWILIO_SENT`
- `TWILIO_DELIVERED`
- `TWILIO_UNDELIVERED`
- `TWILIO_FAILED`
- `TWILIO_CANCELED`

`failed` and `undelivered` do not cause an automatic retry. Those states describe downstream handling of an already-created Twilio Message; automatically resending would create a new message and could produce a duplicate communication.

Non-reconciliation deliveries are not reopened. Their provider object/status evidence is updated only after the same correlation checks.

## Audit model

Provider-generated reconciliation writes append-only `PlatformAuditEvent` evidence with action `platform.integration.delivery.reconciled_by_provider_callback`.

Observed status updates outside reconciliation write `platform.integration.delivery.provider_status_observed`.

Because the callback is generated by Twilio rather than a human platform user, these system audit events deliberately do not fabricate `actorIdentityId` or `actorMembershipId`. Metadata records the provider, inbound receipt, Message SID, provider status, prior Trace delivery status, and automated resolution where applicable.

The operator reconciliation fields (`reconciledAt`, `reconciledByIdentityId`, `reconciledByMembershipId`) remain reserved for the accountable human workflow introduced in PR 19.

## Idempotency and concurrency

Inbound webhook receipt idempotency remains connection-scoped. The original delivery row is locked `FOR UPDATE` while callback evidence is applied, so concurrent callbacks cannot race the reconciliation transition.

A callback does not enqueue a new outbound operation and does not reset attempt count.

## Security boundary

- Provider signature verification remains adapter-owned and occurs before reconciliation logic.
- Connection ID plus delivery key alone is insufficient to mutate state.
- A recorded Message SID cannot be replaced by a different SID.
- No SMS body, Twilio auth token, or arbitrary callback parameter set is copied into delivery evidence.
- Twilio does not gain tenant RBAC, platform RBAC, QMS accountable-user authority, subscription entitlement authority, or support-access authority.
- Callback-driven reconciliation cannot trigger a retry.
