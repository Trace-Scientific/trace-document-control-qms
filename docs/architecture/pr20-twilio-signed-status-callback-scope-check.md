# PR 20 — Twilio Signed Status Callback Enablement

Baseline: `main` at `ea63c7c4036b2796fb0ab4c45ce21761b898fd4c`

## Included

- First focused provider callback enabled on the PR 16 hardened inbound boundary.
- Twilio SMS `StatusCallback` URL generated by the adapter, never supplied by outbound payload callers.
- Existing integration connection ID supplied to provider adapters only as runtime delivery context.
- Opt-in `callbackBaseUrl` configuration restricted to a bare HTTPS origin.
- Exact URL + form-parameter HMAC-SHA1 verification using the configured Twilio Auth Token.
- Twilio `AccountSid` match in addition to signature verification.
- Delivery correlation through the original persisted idempotency key embedded in the signed callback URL.
- Bounded normalization of Message SID, Message Status, delivery key, and optional Error Code.
- Executable regression tests for callback URL generation, valid signature normalization, and rejection of invalid signature/origin.
- Architecture evidence.

## Security invariants

- Existing Twilio connections remain outbound-only unless callback configuration is explicitly enabled.
- Provider credentials remain outside application tables.
- Raw webhook body persistence is not introduced.
- Twilio cannot select an arbitrary callback URL through an outbound event payload.
- A callback is not trusted solely because it knows a connection ID or delivery key; signature and account identity must verify.
- Callback receipt does not grant roles, entitlements, or QMS authority.
- Callback receipt does not automatically resolve a PR 19 reconciliation item in this PR.

## Explicit exclusions

- Automatic reconciliation state mutation from callback events.
- Incoming SMS content workflows.
- MMS/media handling.
- Messaging Service-specific sender behavior.
- SendGrid signed Event Webhook.
- QuickBooks/Zendesk callback expansion.
- Salesforce Pub/Sub CDC.

## Next controlled slice

A subsequent PR may apply verified Twilio status events to provider-delivery reconciliation only after status-to-delivery semantics, terminal/non-terminal behavior, and automated audit evidence are separately reviewed.
